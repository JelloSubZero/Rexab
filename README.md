# Rexab

Rexab — Telegram-бот для совместного ведения расходов в комнате: участники добавляют чеки и платежи, после чего бот рассчитывает долги, показывает итоговый расчёт и помогает закрыть взаиморасчёты через settlement.

## Основные возможности

- создание комнаты и получение кода приглашения;
- присоединение участников по коду;
- защита закрытой комнаты от новых участников;
- хранение участников комнаты;
- добавление чеков и просмотр общей суммы;
- добавление платежей с указанием плательщика;
- удаление платежей;
- автоматический пересчёт долгов после добавления и удаления платежа;
- персональные уведомления об изменении долга;
- итоговый расчёт «кто кому должен»;
- settlement и подтверждение погашения долга;
- автоматическое закрытие комнаты после погашения всех долгов;
- удаление сообщений Telegram, связанных с комнатой;
- хранение идентификаторов сообщений в `room_messages`;
- хранение основного сообщения комнаты в `room_views`;
- QR-приглашение в комнату.

## Работа с сообщениями

Для сообщений, которые должны быть удалены вместе с комнатой, используется:

```text
RoomMessageService
        │
        ├── send()
        │     └── отправляет Telegram-сообщение
        │         и сохраняет chat_id/message_id
        │
        ├── save()
        │
        └── delete_all()
              └── удаляет сообщения из Telegram
                  и записи из room_messages
```

Основное сообщение состояния комнаты хранится отдельно через `RoomView`.

## Транзакции

Репозитории операций изменения данных по возможности не делают промежуточный `commit()`. Для записи используется `flush()`, а итоговый `commit()` выполняется на уровне бизнес-операции.

Например, добавление платежа:

```text
создание платежа
        ↓
история
        ↓
пересчёт долгов
        ↓
уведомления
        ↓
RoomMessage
        ↓
COMMIT
```

Удаление платежа работает по той же схеме:

```text
DELETE payment
        ↓
history
        ↓
пересчёт долгов
        ↓
уведомления
        ↓
RoomMessage
        ↓
COMMIT
```

Это позволяет не фиксировать только часть операции.

## Проверка базы

Для диагностики используются SQLAlchemy/SQLite `PRAGMA`.

Например:

```sql
PRAGMA index_list('room_members');
PRAGMA index_list('room_views');
```

Проверка дубликатов:

```sql
SELECT
    room_id,
    user_id,
    COUNT(*) AS cnt
FROM room_members
GROUP BY room_id, user_id
HAVING COUNT(*) > 1;
```

## Текущий технический фокус

Проект сейчас дополнительно стабилизируется вокруг:

- единого управления транзакциями SQLAlchemy;
- централизованного сохранения Telegram-сообщений;
- защиты от дублей участников и `RoomView`;
- корректного удаления данных комнаты;
- надёжного удаления связанных Telegram-сообщений;
- уменьшения количества разрозненных `commit()` в repositories.

## Важные правила разработки

1. Repository не должен без необходимости самостоятельно завершать бизнес-транзакцию.
2. Изменения данных в рамках одной бизнес-операции должны фиксироваться единым `commit()`.
3. Сообщения, которые должны удаляться вместе с комнатой, должны попадать в `room_messages`.
4. Основное меню/состояние комнаты пользователя должно сохраняться через `room_views`.
5. После изменения схемы SQLite существующую БД нужно обновлять миграцией, а не рассчитывать только на `create_all()`.

## Статус

Проект находится в активной разработке. Основные сценарии создания комнат, участников, платежей, расчёта долгов, settlement и автоматического закрытия комнаты уже реализуются; текущая работа направлена на стабилизацию архитектуры и транзакций.
